# G3: two games from one foundation (in progress, branch `g3/pumpkin-blaster`)

| | Pumpkin Blaster | Trick or Treat Rush |
|---|---|---|
| Orientation, world | landscape, 1920 x 1080 | portrait, 1080 x 1920 |
| Input scheme | `drag` (free movement) + tap to fire | `lanes` (one lane per swipe), no firing |
| Goal | shoot pumpkins (+10) and bats (+25), reach 1000 | survive: distance stripes (+1), candy (+10) |
| Hazards | anything reaching the ship, embers can't be shot | tombstones, ghosts (from 30 s) |
| Difficulty | constant spawn rates | 3 phases over 60 s (`startTick`) |
| End | 5 lives or 1000 points | 3 lives |
| Golden scenarios | 5 (505 checkpoints) | 6 (606 checkpoints) |

Both apps are generated by the same generator and runtime. Neither has game-specific generator code.

## Spec v3 (the only runtime change)

Trick or Treat Rush could not be expressed in v2. Difficulty could not rise, because every spawner ran from
tick 0. Lane switching had no input mapping. Fixed per-lane intervals also always line up eventually (their
LCM), which blocks all three lanes at once: a feasibility check found an unavoidable death on the first draft
schedule. Three additions, all required properties (`docs/SPEC-V2-MIGRATION.md`):

- `spawners[].startTick`: the first spawn tick and the phase (`(tick - startTick) mod intervalTicks == 0`).
  Nothing is drawn before it. `0` is exactly the v2 rule, so all 22 earlier scenarios kept identical recorded
  states; only their spec hash changed. Contract section 4 was updated first, then the oracle with
  hand-computed tests (`test_oracle.SpawnerStartTick`), scenarios, 3 new mutants (all killed), then Kotlin
  and Swift.
- `input.scheme: "lanes"`: shell-only mapping. A horizontal swipe submits `drag(+-swipeSpeed, 0)`. The core is
  unchanged.
- `kinds[].color`: presentation only, never read by the simulation. It replaces the "even kind = primary"
  colouring so the two games look distinct.

Jumping was not added. It isn't needed for a lane runner.

Avoidance in Trick or Treat Rush is checked three ways:

- A schedule check (no tick in 200 s with all lanes blocked).
- The `dodge-run` scenario (a deterministic player keeps all 3 lives for 90 s).
- A one-off run of that player for 20,000 ticks on 4 seeds, all lives kept. That run is not committed.

## Limitations

- Restart is shell behaviour: a new `World` with a new seed. No golden scenario can express it; it was
  observed on the Android emulator only.
- The players in `dodge-run`, `candy-chase` and `win-1000` are scripted bots that read oracle state to
  produce input traces (`tools/monstera/author_scenarios.py`). The checkpoints themselves come only from
  `monstera scenarios record`.
- The distance meter is the score from stripes. There is no separate distance observable.
- Plain rectangles, no artwork and no sound. Entities are not clipped to the world rectangle.
